在着手开始进行DA的各种活动之前，需要先制定战略、路线图，确保做对的事情。本章内容将结合DJI Developer进行分析。

# 了解公司

## 市场地位

了解公司的市场地位、[[职业探索/工程管理/《工程管理导论》计划#^7575b4\|竞争情况]]能帮助DA明确需要以何种力度发声。

+ **市场领导者**：目标是让开发者持续保持参与度，避免用户流失，实现可持续发展；DA能够接触大量的开发者，更具影响力；同时工作必须严谨，与企业形象保持一致，有更大的压力。
+ **挑战者**：DA需要突出产品的差异性，找到竞争者的产品痛点，帮助开发者实现转型。
+ **细分市场参与者**：DA的战略需要聚焦细分市场的开发者，对细分行业有深入的知识和理解，并建设更强的社区凝聚力。
+ **明星企业**：团队规模小，DA需要担任更多的角色，对公司的发展能产生重要影响；需要应对更多的不确定性，从零开始帮助塑造公司的整体形象；投入更多的时间培育开发者社区，提升品牌知名度；提升开发效率，建立清晰的视野、快速的反馈机制，以应对快速变化的环境。

市场地位有时候需要结合特定的产品进行分析，市场领导者可能会进入其他赛道，并推出一款挑战者/明星的产品。

> [!NOTE] 应该加入什么样的公司
> 从上述分类来讲，明星初创企业更需要DA这样的角色，在那里能完整体验DA的职责内容，虽然挑战较大但是成就感更足；同时如果该初创企业属于细分行业，则能降低DA的工作难度，长远能发展成为行业专家。
> 
> 所以，对一位刚入行的DA来说，加入一家自己所热爱行业的初创企业是最理想的选择。


## 成长阶段

了解公司的成长阶段可以指引DA将声音聚焦于何处。

公司的成长阶段可以结合[[职业探索/工程管理/《工程管理导论》计划#^fd2c0b\|产品生命周期模型]]和客户生命周期来分析。

在营销领域，有一个AAARRRP的模型，将客户生命周期划分成7个阶段：**认知（Awareness）、获取（Acquisition）、激活（Activation）、留存（Retention）、创收（Revenue）、推荐（Referral）、产品反馈（Product Feedback）**，这7个阶段和[[职业探索/工程管理/12. What Is Developer Advocacy#^54eccf\|开发者生命周期]]的映射关系如下：

![职业探索/工程管理/assets/13. Developer Advocacy Strategy/8f54b8e8a8934f72fff8fa1562cbe4a4_MD5.png](/img/user/%E8%81%8C%E4%B8%9A%E6%8E%A2%E7%B4%A2/%E5%B7%A5%E7%A8%8B%E7%AE%A1%E7%90%86/assets/13.%20Developer%20Advocacy%20Strategy/8f54b8e8a8934f72fff8fa1562cbe4a4_MD5.png)

7个阶段和产品生命周期的对应关系如下：
+ **投入期**：专注于**认知、获取**早期阶段，需要吸引更多客户；
+ **成长期**：专注于**激活**与**留存**，需要扩大规模并且提升现有客户的体验；
+ **成熟期**：专注于**收入增长**、**客户推荐**及**产品反馈**来实现长期发展；

7个阶段对应的活动重点，如下图所示。

![职业探索/工程管理/assets/13. Developer Advocacy Strategy/2d1ce77e9dbbf7250e324e2273f98b32_MD5.png](/img/user/%E8%81%8C%E4%B8%9A%E6%8E%A2%E7%B4%A2/%E5%B7%A5%E7%A8%8B%E7%AE%A1%E7%90%86/assets/13.%20Developer%20Advocacy%20Strategy/2d1ce77e9dbbf7250e324e2273f98b32_MD5.png)

> [!NOTE] DA应该重点关注什么阶段和活动
> 可以发现DA的活动、内容产出对于**获取、激活**这两个阶段（**即帮助开发者从0到1**）的贡献度最大，这两个阶段也需要花费大量力气才能收获较好的效果。

## 商业模式

在开发者工具领域，存在两种基本商业模式，和对应的四种盈利策略。在不同的商业模式、盈利策略下，DA的重点任务不同。

| 商业模式               | 盈利策略                              | 例子                | DA工作重点                 |
| ------------------ | --------------------------------- | ----------------- | ---------------------- |
| Developer-First 模式 | 收入前置：试用后很快转化为付费客户，按调用量付费。         | 阿里云OSS服务，免费额度有限   | 加快从“尝试”到“实际使用”的速度      |
| Developer-First 模式 | 收入延迟：开发者可能长期免费使用，只有进入大规模生产时才产生收入。 | 企业版、Pro版          | 关注社区建设、长期信任关系的建立       |
| Developer-Plus 模式  | 市场增强：开发者工具本身免费，但能带动核心产品的销售量。      | 华为鸿蒙生态，带动更多鸿蒙设备销售 | 要让核心产品好用，让开发者有信心和意愿去参与 |
| Developer-Plus 模式  | 生态驱动：依赖第三方开发者在其平台上构建应用/内容，并从中分成。  | 微信小程序             | 简化构建应用的流程、展示成功案例       |
+ Developer-First 模式：开发者是第一客户；
+ Developer-Plus 模式：开发者不是最终客户，但赋能核心业务；


# 了解产品

QFD在DA产品分析中的应用。

DA的[[职业探索/工程管理/12. What Is Developer Advocacy#^c9aa06\|首要职责]]是了解自己推广的产品。通过鉴别**产品类别**、**亲自试用与提问**、**分析竞品**、**把握受众**几个阶段来做到对产品全面的认识。

## 产品类别

明确产品所属的类别，有助于制定DA工作的重点。

| 类型         | 特点                                            | 例子         | DA工作重点                                                                                                         |
| ---------- | --------------------------------------------- | ---------- | -------------------------------------------------------------------------------------------------------------- |
| API        | 开发者通过HTTP等方式请求服务端调用                           | 微信支付API    | 1. 完善的API文档<br>2. 多种方式、语言的接口调用示例（如curl、Python）<br>3. 改进错误提示和调试体验<br>4. ....                                    |
| SDK        | 为特定语言/平台封装好的库，                                | 非夕机器人SDK   | 1. 按语言提供教程和多平台特定指南<br>2. 维护SDK变更日志、版本管理<br>3. 录制演示视频<br>4. ....                                                |
| 开发者工具      | 本地优先，集成到开发者日常流程                               | Obsidian插件 | 1. 提供最小化安装指南和配置指南<br>2. 分享“我是怎么用这个工具”、典型真实场景的博客/视频<br>3. 工具与开发者的工作/思维习惯关联性强，因此要收集早期用户反馈，回传工程团队，优化体验<br>4. .... |
| 开发者服务      | 托管平台/服务，通过Dashboard、CLI或API提供基础设施，开发者无需自己搭建后端 | 图床、Vercel  | 1. 演示、快速入门课程<br>2. 提供模板和优秀应用案例<br>3. 解释性能、扩展性、成本权衡                                                             |
| 开发者市场与生态系统 | 平台方提供API和发布机制，第三方开发者创建插件/应用/扩展                | 微信小程序市场    | 1. 培训贡献者如何构建和发布高质量软件包或扩展<br>2. 通过精选内容或推荐系统帮助消费者发现实用工具<br>3. 维护大使/贡献者计划，为资深用户/贡献者提供激励<br>4. ....                |

## 亲自试用

像开发者一样去使用自己的产品，并在使用过程中有意识地进行观察和思考。

| 维度  | 说明                                                                              | 观察和思考                                                                                                                   |
| --- | ------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| 亮点  | 这个维度的研究是在教程和演示中需要重点突出的内容。                                                       | 1. 要达到“哇，这真有用”的时刻需要多长时间？<br>2. 这款产品为何如此令人愉悦？<br>3. 哪些功能快速、简洁或出乎意料地实用？<br>4. ....                                        |
| 摩擦力 | 这块内容需要通过产品优化、教程、演示来减小摩擦和阻碍。<br>**许多产品之所以成功，关键在于减少了用户使用过程中的障碍（即降低了摩擦），而非增加额外功能** | 1. 人们会在哪里遇到障碍？哪些内容令人困惑或缺失？<br>2. 是什么导致开发流程耗时超出合理范围？<br>3. 产品基于哪些假设设计，而在实际应用中这些假设并不成立？<br>4. ...                         |
| 疼痛点 | 这些问题应该交给产品与工程团队处理。                                                              | 1. 缺少了什么才能让这个功能更简单或更强大？<br>2. 哪些因素会直接影响开发者的体验？<br>3. 该产品能否很好地集成到常见的工具链中？<br>4. 该功能是否能与现有工作流程无缝兼容，还是需要进行重大改动？<br>5. .... |

## 目标客户
{ #068042}


分析产品的目标客户，不仅要了解使用你产品的个人，还要掌握他们所属的组织、所处的行业以及产品适用的具体场景。

在用户细分问题上，可以采用**开发者分段框架**，即从**技术层**、**用户层**、**组织层**和**市场层**进行分析。
+ **技术层**：使用的语言、框架、平台或设备能够排除大部分的群体；
+ **用户层**：开发者的身份、职位是什么？是独立工作还是团队协作？是初级员工还是资深员工？他们是在开发副项目、管理持续集成（CI）流程，还是负责架构决策？明确用户身份有助于设计更具备针对性的内容；
+ **组织层**：了解开发者隶属于什么样的组织。该组织的规模如何，组织拥有多少资源，需要达到什么条件才能使用我们产品；组织中谁有采购决策权、谁负责审批、谁是实际使用者？
+ **市场层**：产品适合哪类垂直行业，地区分布，开发者所在行业的监管要求、基础设施、工作流程等特点；

通过以上四方面的分析，我们能构建出理想客户的画像（ICP），这个画像并非描述个人，而是包括了技术条件、开发者角色、组织支持、市场驱动等一些列要素。在这个过程中，可以应用下图所示的**同理心地图画布**。

在组织层面中，需要识别影响采购的相关角色，可能需要为这些角色定制一些内容。

| 角色    | 定义                                         | 需求                | DA的工作                 |
| ----- | ------------------------------------------ | ----------------- | --------------------- |

| 实施者   | 具体使用和集成工具的人                                | 可靠、易用的工具和有帮助的文档   | 分步教程、测试仓库、一键安装脚本等     |

| 批准人   | 掌握预算和审批权的人                                 | 投资回报率、合规性、供应商风险   | ROI计算器、团队启用清单、客户案例PDF |
| 内部推荐者 | 客户公司内部使用过产品并主动推荐的人，往往由满意的用户演变而来，能提升团队的采用信心 |                   | 演讲PPT、成功故事、内部Q&A手册    |



## 竞品分析


> [!NOTE] 
> 当开发者接触到你的项目时，他们并非从零开始；他们带着对上一款工具的固有认知、对上一个失效工作流程的不满，以及对上一款承诺过多却未能兑现的工具所产生的怀疑态度。

竞品分析能够帮助DA更深入地了解目标开发者的需求，以及找到产品的差异化策略。可以通过以下方面来研究竞品：
+ 我们的产品解决的是什么问题，还有谁在解决这个问题？
+ 他们的工具是什么样子的？
+ 他们设定了哪些期望？
+ 开发者们赞扬或吐槽的竞争对手特色？
+ 哪些工作流程尚未得到充分支持？
+ 哪些开发者群体感到被边缘化或忽视？
+ 使用他们的工具有多容易上手？
+ 要多久才能获得有意义的结果？
+ 用户在使用过程中遇到的摩擦点？
+ 他们的文档和技术支持、社区有多完善？
+ 借助真实开发者的报价，帮助营销优化定位
+ ....

相对于竞品的优势，可以通过：
+ 围绕这一快速取胜策略来组织文档；
+ 制作一个演示，展示“哇”时刻。
+ 编写对比指南，温和地指出用户在使用您的方法时会避开哪些方面。

对于自己产品的薄弱之处，也要做出说明，否则可能做出过度承诺，令用户感到失望；而一旦明确指出这些不足之处，就能建立信任。

最后，将竞品的调研成果分享给产品团队。
