# ROS2改进点

ROS2 相比于ROS1的改进主要在以下方面：
+ 去中心化，干掉了Master节点，从星型拓扑演化为网状拓扑，采用了Discovry Server机制（任意两个节点可以自发现并传输消息）；
+ 引入DDS中间件，提供了服务质量QoS的灵活设置、零拷贝支持；
+ 跨平台支持，支持Linux, Windows, macOS, RTOS等；
+ 通过SROS2（Security-Enhanced ROS 2）框架提供加密、认证和访问控制功能；

# ROS2进程部署模式

ROS2 中，节点的运行、编程模式核心分 3 种：**独立节点模式**（Standalone Nodes）、**单进程多节点**（Static Composition）、**动态组件模式**（Dynamic Composition）。

## Standalone Nodes

每个节点（Node）运行在独立的操作系统进程中，通过 DDS 进行通信。这是最传统、隔离性最好的部署方式。

**优点**：节点崩溃互不影响，易于调试和扩展。  
**缺点**：进程间通信（IPC）依靠SHM、UDP进行通信，有序列化/反序列化及网络开销，延迟略高。虽然有SHM共享内存，但是要求数据类型必须是定长，否则虽然节省了本地网络通信成本，但仍然要进行序列化、反序列化。[[机器人世界/ROS小车项目/11. ROS2 点云零拷贝传输方案#^ab0bea\|进程间共享内存实现]]

```cpp
// 创建发布者节点
class PointcloudPublisherNode : public rclcpp::Node {/*...*/}

int main(int argc, char ** argv) {
    rclcpp::init(argc, argv);
    rclcpp::spin(std::make_shared<PointcloudPublisherNode>());
    rclcpp::shutdown();
    return 0;
}
```

```cpp
// 创建订阅者节点
class PointCloudSubscriber : public rclcpp::Node {/*...*/}

int main(int argc, char ** argv) {
    rclcpp::init(argc, argv);
    rclcpp::spin(std::make_shared<PointCloudSubscriber>());
    rclcpp::shutdown();
    return 0;
}
```


## Static Composition
{ #cea5cb}


在一个进程中创建多个 `rclcpp::Node` 实例，通常使用单个或多个执行器（Executor）管理它们。

**优点**：避免了进程间通信开销，可以通过手动设置`use_intra_process_comms=true`来启用零拷贝，但是发布者和订阅者属于同一个 `rclcpp::Context`（即在同一个`rclcpp::init()`中），消息类型要支持 `UniquePtr` 或 `SharedPtr`，否则会回退到序列化模式。
**缺点**：运行在同一个进程地址空间中，因此没有内存隔离，一个节点的内存越界，可能导致整个进程崩溃。

```cpp
class PointcloudPublisherNode : public rclcpp::Node {/*...*/}
class PointCloudSubscriber : public rclcpp::Node {/*...*/}

int main(int argc, char ** argv) {
  rclcpp::init(argc, argv);
  rclcpp::executors::SingleThreadedExecutor executor;
  auto talker_node = std::make_shared<PointcloudPublisherNode>();
  auto listener_node = std::make_shared<PointCloudSubscriber>();
  executor.add_node(talker_node);
  executor.add_node(listener_node);
  executor.spin();
  rclcpp::shutdown();
  return 0;
}
```

除了使用`SingleThreadedExecutor`，也可以使用多线程`MultiThreadedExecutor`，若启用了`use_intra_process_comms`， `IntraProcessManager`内部也是线程安全的（移交消息指针）。
- 单线程执行器：回调按顺序执行，无并发。
- 多线程执行器：回调在线程池中并发执行，可通过 `CallbackGroup`（互斥或可重入）控制同一节点内回调的并发度。

执行器不区分节点，只按照回调的就绪状态调度。如果某个节点产生大量高频率回调，可能占用较多线程资源，影响其他节点的响应。

## Dynamic Composition
{ #8027da}


和Static Composition的机制相同，都是单进程多节点，零拷贝方式完全相同。区别在于动态组件模式将节点封装为`.so`动态库，在运行**容器进程**（`rclcpp_components::ComponentContainer`）后，可以懒加载这些动态库节点，而不是硬编码在一个cpp文件中。

**优点**：避免了进程间通信开销，和Static Composition可以实现零拷贝，支持运行时动态加载/卸载，便于系统集成。  
**缺点**：没有内存隔离，实现稍复杂；

| 维度       | 独立节点进程                                                                                                       | 静态组件模式                                                            | 动态组件模式                                                                                                    |
| -------- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| **进程模型** | 1 节点 = 1 独立进程                                                                                                | 多节点 = 1 个进程<br>手动在 `main` 函数创建多个节点                                | 多节点 = 1 个进程<br>动态加载组件库到容器进程                                                                               |

# DDS通信原理
{ #8dc6e0}

在消息即使性与可靠性的取舍上，ROS2可配置的机制包括：共享内存（iceoryx/FastDDS）、Qos、消息序列化、消息历史保存机制、UDP（话题默认UDP）和TCP。

## QoS
{ #97b92c}


### 策略

通过 QoS 策略，可以让通信像TCP一样可靠，或像UDP一样尽力而为，甚至实现更多中间状态。Qos 由一组 “**策略**（Policies）” （一组设置项）组合而成。

| 策略类型               | 可选值                                                 | 作用说明                                                                                                                                                           |
| ------------------ | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **History**        | `Keep last`（保留 N 个）、`Keep all`（保留所有）                | 定义消息队列的保留方式，`Keep last` 需配合 `Depth` 使用。                                                                                                                        |
| **Depth**          | 数值（如 10）                                            | 队列大小，仅在 `History=Keep last` 时生效。                                                                                                                               |
| **Reliability**    | `Best effort`（尽力而为）、`Reliable`（可靠）、`Best Available` | `Best effort` 没有重传但实时性高；`Reliable` 有重试机制（但重传次数不能设置），保证送达（基于 UDP 实现，支持组播）。<br>`Best Available`能够做到策略兼容情况下自动选择最高策略。                                              |
| **Durability**     | `Volatile`（不持久化）、`Transient local`（持久化）             | 由于话题的订阅者有多个，`Transient local` 让 “晚加入” 的订阅者收到历史消息（类似 ROS1 的 latching），但是如果发布者已经不存在了则不会收到任何消息。<br>持久化存多少消息由`History` 和 `Depth` 决定（默认只有10条），此外也会受DDS中间件的内存配置限制。   |
| **Deadline**       | 时间间隔（如 500ms）                                       | 发布者承诺的「最大消息发布间隔」：我保证每隔 X 时间必须发一条消息。<br><br>如果超过这个时间没发布新消息，就会触发超时事件。<br><br>主要用于检测发布者消息频率发布是否正常。例如IMU 传感器要求200Hz发布，如果超过 10ms 没发消息则认为异常。<br><br>默认值无限大，即不启用超时检测。 |
| **Lifespan**       | 时间间隔（如 1s）                                          | 如果消息在有效期内没被订阅者接收，就会被静默丢弃。<br>主要用于一些有时效的消息，例如障碍物信息，避免控制模块使用过期的障碍物位置导致撞墙。<br>默认值无限大，即不会过期。                                                                       |
| **Liveliness**     | `Automatic`（自动）、`Manual by topic`（手动）               | 主要是发布者向订阅者发心跳，如果没心跳了，相当于节点死掉了。和Deadline有点像，但Deadline超时只是没法消息，不代表节点挂了。<br>定义 “保活” 方式：`Automatic` 发布消息即保活；`Manual` 需手动调用 API。<br>默认是自动。                          |
| **Lease Duration** | 时间间隔（如 2s）                                          | Publisher 保活的最大周期，超时则被视为 “失效”。<br>                                                                                                                             |

### 消息队列

一个节点可以有多个发布者，但一个发布者只能绑定一个话题，每一个话题则拥有一个History + Depth维护的消息队列，同时服务于两个独立功能：

| 功能          | 作用                                                              | 触发条件                                   |
| ----------- | --------------------------------------------------------------- | -------------------------------------- |
| **1. 重传缓存** | 存储已发送但未收到 ACK 的消息，用于 `Reliable` 模式下的丢包重传。                       | 仅在 `Reliable` 模式下生效。                   |
| **2. 历史缓存** | 存储已发送的消息（无论是否收到 ACK），用于 `Transient local` 模式下给 “晚加入的订阅者” 发历史数据。 | 仅在 `Durability = Transient local` 时生效。 |
和MissionCenter不同，MC在dds/mqtt消息重试逻辑中，对于每个topic只维护一个等待ack的消息进行重传，如果这个topic有新的消息发布，那么旧值就会被移出重传队列。

那么为什么ROS2要维持depth>1的消息队列？这个消息队列的用处是什么？这两个问题将在下面的不同配置策略中进行解释。

### 预配置策略

ROS2 在`qos.hpp`中提供了针对常见场景的预配置，避免手动调整每个策略。

#### SystemDefault

和具体的DDS中间件实现有关，不同的DDS存在不同默认值。其他配置中采用DEFAULT的也如此。

#### LatchedPublisherQoS

KeepLast(1)`+`reliable`+`transient_local。这个策略不是ros官方库的，但是很多项目实际都会经常用到。
- **有重传缓存** + **有历史缓存**（两者共用同一个队列）；
- **队列长度为1**：
    1. 消息发布后先存入队列；
    2. 收到订阅者的 ACK 后，**不会移除**（因为要留给晚加入的订阅者）；
    3. 如果来了新消息，由于队列长度为1，会直接覆盖最旧的消息；
    4. 晚加入的订阅者会收到队列里当前最新的这个消息。

这个就类似MissionCenter中的state消息，主要是一些偶尔更新类的状态数据，例如静态TF坐标、地图数据，晚加入的节点需要这些数据完成初始化。通常用`Keep last(1)`，只保留最新的一条状态消息，既满足了晚加入者的需求，又不会占用太多内存。

#### rclcpp::SensorDataQoS

`Keep last(5)` + `Best effort` + `Volatile`。

- **没有重传缓存**（因为 `Best Effort` 不关心 ACK）；
- **没有历史缓存**（因为 `Volatile` 不持久化）；
- **队列行为**：消息发出去就立即从队列里移除，队列几乎是空的。

这个就类似MissionCenter中的定频osd消息；适用于相机图像、点云、IMU数据等要求实时性>可靠性的定频数据。

#### rclcpp::ServicesQoS

`Keep last(10)` + `Reliable` + `Volatile

- **有重传缓存**：存储 “已发送但未收到 ACK” 的消息；
- **没有历史缓存**（因为 `Volatile` 不持久化）；
- **队列行为**：
    1. 消息发布后先存入队列；
    2. 收到所有订阅者（多订阅者情况）的 ACK 后，从队列里移除；
    3. 如果队列满了（达到 `Depth`），新消息会覆盖最旧的未 ACK 消息。

主要适用于即时指令型消息，如去目标点、急停等，需要可靠送达，但不需要给晚加入者发历史数据。

#### rclcpp::ParametersQoS

`Keep last(1000)` + `Reliable` + `Volatile`


#### rclcpp::RosoutQoS

`KeepLast(1000)`+`Reliable`+`TRANSIENT_LOCAL`+`Lifespan(0,10)`。负责节点日志（INFO/WARN/ERROR）的可靠传输与记录

#### rclcpp::ClockQoS

`Keep last(1)`+`Best effort`+`Volatile`。负责进程间时间同步。


### QoS 兼容性规则

Publisher 与 Subscriber 的 QoS 必须**兼容**才能建立连接，遵循 “**请求 vs 提供**” 模型：

- Subscriber **请求**（Request）：能接受的 “最低质量”；
- Publisher **提供**（Offered）：能提供的 “最高质量”；
- 只有当 Publisher 的质量 ≥ Subscriber 的要求时，连接才会建立。

### 代码实现

#### Default Qos

创建一个Default类型的Qos配置。

```cpp
rclcpp::QoS qos(10);
publisher_ = this->create_publisher<learning_topic::msg::Person>("/person_info", qos);

# 或者使用隐式构造
publisher_ = this->create_publisher<learning_topic::msg::Person>("/person_info", 10);
```

| QoS 策略         | 值              |
| -------------- | -------------- |
| History        | Keep last      |
| Depth          | 10             |
| Reliability    | Reliable       |
| Durability     | Volatile       |
| Liveliness     | System default |
| Deadline       | Default（无限）    |
| Lifespan       | Default（无限）    |
| Lease Duration | Default（无限）    |
可以在Default类型的基础上更改配置：
```
rclcpp::QoS qos(10);
qos.reliability(RMW_QOS_POLICY_RELIABILITY_BEST_EFFORT);

# 或者直接调用
qos.reliable();
qos.best_effort();
```

#### 兼容性回调

订阅者可以注册qos不兼容回调：

```cpp
// 订阅“QoS 不兼容”事件（通过 SubscriptionOptions，而非 create_subscription 第 5 个参数）
rclcpp::SubscriptionOptions sub_options;
sub_options.event_callbacks.incompatible_qos_callback =
	[this](rclcpp::QOSRequestedIncompatibleQoSInfo & info) {
	RCLCPP_WARN(
		this->get_logger(), "❌ Incompatible QoS! Last policy kind: %d",
		info.last_policy_kind);
};

subscriber_ = this->create_subscription<std_msgs::msg::String>(
	"qos_test_topic", qos,
	std::bind(&QoSSubReliable::topic_callback, this, std::placeholders::_1),
	sub_options);
```

当发布者为`Reliability=Best Effort`，订阅者`Reliability=Reliable`时，就会触发回调，kind为16，`qos_policy_kind`定义如下：
```cpp
/// QoS Policy Kinds
typedef enum RMW_PUBLIC_TYPE rmw_qos_policy_kind_e
{
  RMW_QOS_POLICY_INVALID = 1 << 0,
  RMW_QOS_POLICY_DURABILITY = 1 << 1,
  RMW_QOS_POLICY_DEADLINE = 1 << 2,
  RMW_QOS_POLICY_LIVELINESS = 1 << 3,
  RMW_QOS_POLICY_RELIABILITY = 1 << 4,
  RMW_QOS_POLICY_HISTORY = 1 << 5,
  RMW_QOS_POLICY_LIFESPAN = 1 << 6,
  RMW_QOS_POLICY_DEPTH = 1 << 7,
  RMW_QOS_POLICY_LIVELINESS_LEASE_DURATION = 1 << 8,
  RMW_QOS_POLICY_AVOID_ROS_NAMESPACE_CONVENTIONS = 1 << 9,
} rmw_qos_policy_kind_t;

```
