# 为什么使用行为树

首先我们谈一谈，在智能体的状态-行为逻辑设计中，如果新增一个状态或者行为会发生什么事情。

行为通常是和状态绑定的，即一个行为只可能发生在某些状态下。因此新增一个行为的一般做法是检查每个状态，如果满足行为发生的条件，就在该状态所属的逻辑代码中添加该行为函数的调用。

状态变量很可能是通过枚举实现的，所以新增状态首先需要修改枚举的定义；其次状态变量通常出现在两个地方：条件判断语句、状态切换语句。因此新增一个状态意味着要新增条件分支，然后还需要检查每个原有状态，如果满足条件，就要添加切换至新状态的语句。

明白了上述这些，我们再逐一分析可供选择的代码实现方案。

最下策的方案是通过if...else或者switch...case把不同状态下的行为逻辑堆积出来，当逻辑变得庞杂时，要新增和修改一个状态或者行为就变得异常困难（最大的问题你根本不知道要修改哪些代码，除非你花上半天时间重理一下旧的逻辑体系）。

稍微好一点的方法是采用状态模式，把状体抽象成一个基类，具体类主要负责特定状态下动作选择和状态切换的逻辑，如此一来就可以很方便地找到需要修改的代码位置。但是这种方式还是避免不了不同状态类间的高耦合，即新增一个状态类时，还需要修改原有状态类中的状态切换逻辑。

最优的方法是将一些基本逻辑单位如条件判断、选择、顺序执行抽象为一个个功能节点，最终把这些节点组合为一个树来形成了一套完整的逻辑。就像虚拟引擎UE4那样，通过画框图的形式构建决策逻辑，基本不用修改代码，你只需要理解你自己画的框图，然后添加、挪动一些节点就可以形成新的逻辑。

总结一下行为树的主要优点的话，我认为有两点：**高复用**和**易扩展**。

# 节点的状态

行为树中的所有节点都有以下四个状态：

+ **IDLE**： 初始时候的默认状态
+ **RUNNING**： 节点正在运行。对于一个行为节点，比如赶往学校，必然不可能一蹴而就——当行为树再次遍历到该节点，发现这个节点处于RUNNING状态，就不会去干扰它，转而进行下次遍历，同时也不会再开启新的行为节点，除了并行节点和被强制终止的情况，后者可以理解为队友需要自己紧急支援，于是“干死对面”这个行为被意外终止了。
+ **SUCCESS**：哈哈~终于把对面干趴了，所以状态从RUNNING转到SUCCESS。
+ **FAILURE**: 敌人逃跑，丢失攻击目标，状态从RUNNING转到FAILURE。




# 节点的类型

RoboRTS中用到的节点类型：

+ **ActionNode**：动作节点
+ **SelectorNode**： 选择节点
+ **SequenceNode**： 序列节点
+ **ParallelNode**： 并行节点
+ **PreconditionNode**： 前置条件节点

实际中使用较为频繁的是动作、选择、前置条件节点。



## ActionNode

动作节点，一般是行为树的叶子节点，具有对外界的动作，如烧水、挖矿、回家等。除了它以外的节点类型都可以看做是逻辑节点。



## SelectorNode

选择节点，从左到右依次访问child，一旦有一个child节点成功运行了，那么这个选择节点也就运行成功了；如果所有child们都运行失败，那么这个选择节点也就运行失败。



## SequenceNode

序列节点，从左到右依次运行child，一旦有一个child运行失败，那么这个序列节点也就终止，返回失败状态；如果全部child们依次运行成功，那么序列节点也成功。



## ParallelNode

并行节点，同时启动多个child节点，例如”休息“和”烧水“两个动作可以同时进行。



## PreconditionNode

前置条件节点，修饰一个child，就是一个决定child是否可以被执行的条件，比如是否放学的条件。

## BehaviorNode

总的抽象类，上述所有节点类都直接或间接继承于它。

Run()是它最重要的一个方法，其中调用了节点的OnInitialize()、Update()、OnTerminate();初始化OnInitialize操作仅在节点被启动时调用，OnTerminate操作仅在节点运行结束时调用，所以一直处于RUNNING状态的节点只运行状态更新方法Update()。

```
BehaviorState Run()
{
    // 连续性假设：行为通常会持续多次遍历周期，因此节点处于RUNNING状态是常见的
    // 当重新遍历行为树时，如果遇到了RUNNING的节点，就不再需要初始化操作了
    if (behavior_state_ != BehaviorState::RUNNING)
    {
        OnInitialize();
    }

    // Update中又会调用子节点的Run,因此状态的返回、节点的终止都是由内而外
    behavior_state_ = Update();

    if (behavior_state_ != BehaviorState::RUNNING)
    {
        OnTerminate(behavior_state_);
    }
    return behavior_state_;
}
```

Update()方法对于逻辑节点来说，就是调用child的Run，因此Run和Update是互相嵌套调用，这样一来，在main.cpp中我们只要执行`root_node->Run()`，就可以把整棵行为树运行起来。

**这里的遍历与二叉树的先序遍历类似！**

Update()对于动作节点来说，则是用来调用外部执行器对环境造成影响，然后根据执行器动作结果来决定自己的新状态，比如云台射击对方步兵，云台就是执行器，动作是射击，执行器结果是没打中，节点的新状态就是FAILURE。

Reset()是对结束节点操作的一个补充，Run()中的结束操作不能在RUNNING状态下使用，而Reset是专门用于RUNNING状态下来强制终止节点运行的。




## ActionNode

属性方法基本和BehaviorNode一样。实际编写写行为代码时，只需要实现初始化、更新、结束三个操作即可。下面简单看看吉林大学的一个追击目标的例子，

初始化阶段告诉黑板“我要开始追人了，并且追的是最近的敌人，那，这是它的编号“。
```
virtual void OnInitialize() {             
    blackboard_ptr_->SetChase(true);
    int chase_enemy_num = blackboard_ptr_->GetNearEnemyNUm();
    blackboard_ptr_->SetChaseEnemyNUm(chase_enemy_num);
}
```

更新阶段，当敌人在追击范围内时，节点通过一个目标工厂规划出一条追击的最短路径并调用底盘执行器沿着路径前进，将执行器状态的更新结果作为节点自己的状态。
```
virtual BehaviorState Update() {
    // 根据敌我距离判断是否进行追击
    if(!blackboard_ptr_->IsChase()){
        goal_factory_ptr_->CancelGoal();
        return BehaviorState::SUCCESS;
    }
    goal_factory_ptr_->ChaseGoal();
    blackboard_ptr_->SetActionState(chassis_executor_ptr_->Update());
    return blackboard_ptr_->GetActionState();
}
```

结束阶段是告诉黑板和目标工厂”任务取消“。
```
virtual void OnTerminate(BehaviorState state) {
    switch (state){
    case BehaviorState::IDLE:
        goal_factory_ptr_->CancelGoal();
        break;
    case BehaviorState::SUCCESS:
        blackboard_ptr_->SetChase(false);
        break;
    case BehaviorState::FAILURE:
        break;
    default:
        return;
    }
}
```

## CompositeNode

相比于BehaviorNode，多了对child的处理：内部维护了一个vector，来存储child们的指针；此外，我们还需要知道当前运行的child是哪个，所以内部children_node_index_来指示其在vector中的位置。

之所以在添加child的时候，需要设置parent，是因为这样child才能拜访自己的兄弟。
```
virtual void AddChildren(const BehaviorNode::Ptr &children_node_ptr{
    children_node_ptr_.push_back(children_node_ptr);
    children_node_ptr->SetParent(shared_from_this());
}

std::vector<BehaviorNode::Ptr> children_node_ptr_;
// 记录当前正在或待运行的节点编号
unsigned int children_node_index_;
```

## SelectorNode

我们先来看简化版的选择节点实现：

AddChildren方法和CompositeNode一样。
```
virtual void AddChildren(const BehaviorNode::Ptr &children_node_ptr){
    CompositeNode::AddChildren(children_node_ptr);
}

```

OnInitialize中将待运行节点设置为第一个，符合从左到右的优先级。

```
virtual void OnInitialize(){
    children_node_index_ = 0;
}
```

while只有在child状态结果为FAILURE时才继续循环，否则就```return state```, 如果所有节点都失败，那么SelectorNode的状态也是FAILURE。

```
while (true)
{
    // 运行子节点
    BehaviorState state = children_node_ptr_.at(children_node_index_)->Run();
    if (state != BehaviorState::FAILURE)
    {
        // 每次行为树遍历只运行一个节点
        // RUNNING： 下次继续从该节点开始访问
        // SUCCESS： 在Run()中调用Terminate
        return state;
    }
    // 当所有子节点运行失败时，终止自己（返回FAILURE状态）
    if (++children_node_index_ == children_node_ptr_.size())
    {
        children_node_index_ = 0;
        return BehaviorState::FAILURE;
    }
}

```

以WestWorld项目为例（请参考上文给出的node结构图），mine_selector有两个节点，如果太累了，他就选择回家，在回家的路上，go_home_from_school_action应一直处于RUNNING,因此mine_selector也是RUNNING，当他回到家中时，go_home_from_school_action变为SUCCESS,于是mine_selector也变成SUCCESS。另一天，他在矿地精力充沛打算继续采矿，那么is_rich_or_energy_low_condition就是FAILURE，但是mine_selector并不马上变为FAILURE，而是会去考察一下minning_action，然后......

## ParallelNode

并行节点还定义了一个```children_node_done_```，主要用于记录哪些child已经运行完毕。success_count_是对已经运行完毕的且运行结果是SUCCESS的节点的计数，failure_count_则相反。

```
virtual void OnInitialize(){
    success_count_ = 0;
    failure_count_ = 0;
    children_node_done_.clear();
    // 节点默认标记为false，表未曾访问
    children_node_done_.resize(children_node_ptr_.size(), false);
}
```

从下面的循环中，可以发现```child->Run()```操作只对children_node_done_是false标记的节点有效，也就是没有运行完毕的，这些节点状态可以是IDLE和RUNNING。如果状态一旦变成SUCCESS或FAILURE,children_node_done_标记就会被设置为true。

并行节点自身的状态是由success_count_和threshold决定的，如果SUCCESS的child数超过threshold_，则并行节点和其正在运行的child都被终止，并行节点返回SUCCESS状态；如果FAILURE的节点数过多，同样终止并行节点和其child们，并行节点返回FAILURE状态（FAILURE太多，即使剩下的child都SUCCESS，也达不到threshold了）。

```
virtual BehaviorState Update()
{
    for (unsigned int index=0; index<children_node_ptr_.size(); index++)
    {
        // 仅运行未曾执行完毕的节点
        if (children_node_done_.at(index)==false)
        {
            // 运行子节点
            BehaviorState state = children_node_ptr_.at(index)->Run();

            if (state == BehaviorState::SUCCESS)
            {
                //标记已运行
                children_node_done_.at(index) = true;
                // 当成功次数超过设定值时，并行节点终止自己（返回SUCCESS状态）
                if (++success_count_ >= threshold_)
                {
                    return BehaviorState::SUCCESS;
                }
            }
            else if (state == BehaviorState::FAILURE)
            {
                //标记已运行 
                children_node_done_.at(index) = true;
                // 运行失败的节点数量超过一定数量（也就是说即使剩下来的节点全部执行完都达不到SUCCESS要求）
                if (++failure_count_ >= children_node_ptr_.size()-threshold_)
                {
                    return BehaviorState::FAILURE;
                }
            }
        }
    }

    // 有多个节点还处于RUNNING状态，等待下一次行为树遍历继续执行
    return BehaviorState::RUNNING;
}
```

以WestWorld项目为例，threshold_设置为2,home_parallel是一个并行节点，因为一开始heat_water_action和rest_action的状态都是IDLE,所以在这一次遍历中这两个节点都被启动，变为RUNNING状态。经过几次树的遍历周期后，水烧好了，heat_water_action返回SUCCESS,此时success_count_=1，又经过几次周期后，旷工休息好了，rest_action也返回
SUCCESS，此时success_count_=2，达到了threshold_，所以home_parallel返回SUCCESS。

当然不排除烧水过程中煤气用光的情况，此时heat_water_action返回FAILURE,将导致home_parallel也返回FAILURE（游戏BUG就这样诞生了）。

## PreconditionNode

这个节点初始化时需要提供一个precondition_function_，其返回类型是bool,也就是条件判断函数，这个函数交由Precondition()方法调用

```
virtual bool Precondition()
{
    if (precondition_function_)
    {
    return precondition_function_();
    }
    return false;
}
```

需要注意一点，precondition_function_的类型是std::function<bool()>，也就是说该函数不能带参，不要试图传递一个类的普通成员函数，因为它是默认含this参数的（可以使用lambda或bind辅助）。


前置条件节点可以和选择、序列、并行等节点搭配，由于选择节点涉及到了优先级选择的问题，因此当前置条件节点与选择节点搭配时，需要考虑其终止类型（AbortType）。

前置条件节点的终止类型（AbortType）有四种，除与选择节点搭配的情况，都只选择SELF类型。
+ NONE : 前提条件失效，相当于条件一直满足，直接返回true（用于调试）
+ SELF : 当前提条件为true时，允许执行child；当前提条件为false时，禁止child执行（若child处于RUNNING状态，则立即终止）
+ LOW_PRIORITY ： 当前提条件为true时，立即终止右侧低优先级兄弟（是选择节点的child，与条件节点同级），转而执行child；当前提条件为flase时，禁止child执行（但若child处于RUNNING状态，会允许其继续执行）
+ BOTH ： SELF+LOW_PRIORITY；当前提条件为true时，立即终止右侧低优先级兄弟，转而执行child；当前提条件为false，禁止child执行（若child处于RUNNING状态，则立即终止）

以WestWorld项目为例，is_schoolover_condition是一个BOTH类型的条件节点，而is_mine_condition是SELF节点。对于is_mine_condition来说，如果条件为false,那么不会继续执行mine_selector,即使此时minning_action正处于RUNNING状态，is_mine_condition也会试图强制其终止。而is_schoolover_condition显得更为强硬，意思是当旷工下班准备回家时（minning_action正处于RUNNING状态），突然想到自己的女儿即将放学，而is_schoolover_condition优先级是比is_mine_condition更高的，于是is_mine_condition这条分支上的所有节点应当被强制终止，转而执行is_schoolover_condition分支。

我们来看看代码具体是如何实现这样的功能的。

简单来说，selector依赖children_node_index_做到了这一点。

children_node_index_表示当前正在运行或待运行节点，如果没有下面这段for循环，while就会从children_node_index_开始访问节点，排在children_node_index_之前的节点就被忽略；for做的事情就是去访问排在children_node_index_之前的节点。

children_node_reevaluation_在节点创建的时候初始化，标记了那些child”有特殊能力“(会终止低优先级child),显然，我们的is_schoolover_condition应该会被标记为true，然后在for中被调用Run()方法。

```
BehaviorState SelectorNode::Update()
{
    // 查看是否需要终止低优先级节点（即当前运行节点children_node_index_）
    for (unsigned int index=0; index<children_node_index_; index++)
    {
       if (children_node_reevaluation_.at(index))
        {
            BehaviorState state = children_node_ptr_.at(index)->Run();
            // Run时如果低优先级被成功终止了（即高优先级节点的准入条件得到满足），
            //则children_node_index_会被设置为index
            if (index == children_node_index_)
            {
                // 同下面的while
                if (state != BehaviorState::FAILURE)
                {
                    return state;
                }
                // 如果高优先级节点没有运行成功，则while循环从下一个节点开始遍历
                ++children_node_index_;
                break;
            }
        }`
    }

    while (true)
    {
        //循环同上，省略
    }
}
```

如何让is_schoolover_condition代替低优先级节点运行？我们来看看PreconditionNode的Reevaluation()方法，这个方法在Run()中被调用。

下面这堆东西就是为了判断当前的PreconditionNode是不是排在children_node_index_之前。

```
//BehaviorNode 没有GetChildren等派生类的方法，因此不能用多态指针
auto parent_selector_node_ptr = std::dynamic_pointer_cast<SelectorNode>(parent_node_ptr_);
auto parent_children = parent_selector_node_ptr->GetChildren();
auto iter_in_parent = std::find(parent_children.begin(), parent_children.end(), shared_from_this());
// 意外，没找到
if (iter_in_parent == parent_children.end()) {
    std::cerr << "Can't find current node in parent!" << std::endl;
    return false;
}
// 计算当前选择节点在parent_children中的位置
unsigned int index_in_parent = iter_in_parent - parent_children.begin();
```

关键的是这段，当这个PreconditionNode条件是true的时候，就要终止低优先级的兄弟了，调用了上文提到的Reset方法，然后把children_node_index_改成了自己的编号，真是令人讨厌啊～
```
if(Precondition())
{
    // 终止掉低优先级节点
    parent_children.at(parent_selector_node_ptr->GetChildrenIndex())->Reset();
    parent_selector_node_ptr->SetChildrenIndex(index_in_parent);
    // 还没有终止子节点
    return true;
}
```
