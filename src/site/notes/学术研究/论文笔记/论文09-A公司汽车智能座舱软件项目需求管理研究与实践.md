# 概要

针对座舱软件的需求管理，从需求获取与分析、定义与评估、跟踪与变更三个阶段入手，识别了需求遗漏/错误、需求传递偏差、需求评审不充分、需求跟踪与变更工具和流程不规范等问题，并提出了相应的优化方法：
+ 需求获取与分析：建立需求池和平台功能路线图；
+ 需求定义与评估：用AHP、QFD方法实现需求拆解、排序、开发要素定权、竞品分析；在评审流程中引入FMEA方法；
+ 需求跟踪与变更管理：优化了JIRA工作流。
最后介绍了优化方法在实际项目中的应用细节与效果。

其次，路线图纵向上可以体现发布版本、内部迭代小版本、迭代特性列表等内容。

优点：
+ 可以解决机型功能差异问题；
+ 能将平台/SDK的开发计划展示给下游模块；
+ 可依据这个进行发布版本的RN编写；
局限性：
+ 路线图需要动态维护，如何自动得与其他平台（如JIRA）关联？

### QFD

在AHP拆解的基础上，使用QFD对开发要素进行权重计算、以及竞品分析。

![论文09-A公司汽车智能座舱软件项目需求管理研究与实践-1772539383281.png](/img/user/%E5%AD%A6%E6%9C%AF%E7%A0%94%E7%A9%B6/%E8%AE%BA%E6%96%87%E7%AC%94%E8%AE%B0/assets/%E8%AE%BA%E6%96%8709-A%E5%85%AC%E5%8F%B8%E6%B1%BD%E8%BD%A6%E6%99%BA%E8%83%BD%E5%BA%A7%E8%88%B1%E8%BD%AF%E4%BB%B6%E9%A1%B9%E7%9B%AE%E9%9C%80%E6%B1%82%E7%AE%A1%E7%90%86%E7%A0%94%E7%A9%B6%E4%B8%8E%E5%AE%9E%E8%B7%B5/%E8%AE%BA%E6%96%8709-A%E5%85%AC%E5%8F%B8%E6%B1%BD%E8%BD%A6%E6%99%BA%E8%83%BD%E5%BA%A7%E8%88%B1%E8%BD%AF%E4%BB%B6%E9%A1%B9%E7%9B%AE%E9%9C%80%E6%B1%82%E7%AE%A1%E7%90%86%E7%A0%94%E7%A9%B6%E4%B8%8E%E5%AE%9E%E8%B7%B5-1772539383281.png)

开发要素可以是系统的各个模块，或者是技术指标，如实时性、可靠性等。

优点：
+ 竞品分析这个维度挺有启示的，以前在需求开发过程中从来不会考虑这个维度，以后可以从技术指标、子功能维度进行对比（维度需要按照需求/产品来重新设计）；
+ 对于FO、版本PL可以根据QFD结果识别风险模块或者风险指标；
局限性：
+ 实际上，开发要素的权重价值并不是很大，特别是针对一个需求的拆解项而言，一般肉眼能直接看出；
+ QFD更实用的从一堆需求中去找到关键的技术特征，然后设立技术攻关；以及结合瀑布模型描述需求到底层的参数设计；[[职业探索/质量管理/无人机库质量可靠性分析#^7e9174\|无人机库质量可靠性分析#^7e9174]]

## 需求定义与评估

### FMEA
{ #8d1f1d}


考虑流程引入的工作量，在原有FMEA方法上做了精简，去除了探测度、频度等指标。
![论文09-A公司汽车智能座舱软件项目需求管理研究与实践-1772542020229.png](/img/user/%E5%AD%A6%E6%9C%AF%E7%A0%94%E7%A9%B6/%E8%AE%BA%E6%96%87%E7%AC%94%E8%AE%B0/assets/%E8%AE%BA%E6%96%8709-A%E5%85%AC%E5%8F%B8%E6%B1%BD%E8%BD%A6%E6%99%BA%E8%83%BD%E5%BA%A7%E8%88%B1%E8%BD%AF%E4%BB%B6%E9%A1%B9%E7%9B%AE%E9%9C%80%E6%B1%82%E7%AE%A1%E7%90%86%E7%A0%94%E7%A9%B6%E4%B8%8E%E5%AE%9E%E8%B7%B5/%E8%AE%BA%E6%96%8709-A%E5%85%AC%E5%8F%B8%E6%B1%BD%E8%BD%A6%E6%99%BA%E8%83%BD%E5%BA%A7%E8%88%B1%E8%BD%AF%E4%BB%B6%E9%A1%B9%E7%9B%AE%E9%9C%80%E6%B1%82%E7%AE%A1%E7%90%86%E7%A0%94%E7%A9%B6%E4%B8%8E%E5%AE%9E%E8%B7%B5-1772542020229.png)

优点：
+ FMEA的方法清晰、充分，结果可以作为风险项跟进。以前需求开发中，风险点没有强制开发输出，导致风险点很多是零散地发现的。重点还是在于风险能够跟进（需求跟踪）。
+ 在需求定义阶段执行，能够预防失效。
缺点：
+ 在开发过程中，可能会有新的失效发现，此时要求这个FMEA表能够动态更新维护；
+ 对开发人员还是带来了一定的工作量，如果后续没有跟踪解决，那意义不大。
