# 概述

传输层协议为运行在不同主机上的**进程**提供了一种**逻辑通信机制**。发送方将应用层递交的报文分成一个或多个**报文段（Segment）**，并向下传给网络层；接收方将接收到的段组装成消息，并向上交给应用层。

传输层为应用层提供了**UDP**和**TCP**两大服务。UDP是不可靠的交付服务，仅仅是对网络层接口的简陋包装，没有做可靠性方面的扩展；而TCP是可靠、按序的交付服务，利用**连接控制**、**差错控制**、**流量控制**和**拥塞控制**机制来保证可靠的数据传输，是传输层的精华所在。虽然如此，无论是UDP还是TCP服务，都没有实现时延和带宽方面的保障。

除此之外，传输层还需要借助**多路复用/解复用**和**SAP寻址**的技术将网络层上交的数据分发给主机上正确的进程，以及为不同进程下发的数据附加上进程端口号信息。



# 多路复用和解复用

主机上存在多个进程，所以需要进行多路复用和解复用。

+ 发送端进行多路复用：从多个进程（Socket）接收数据，为每块数据封装上头部信息，生成报文段，交给网络层。
+ 接收端进行解复用：传输层依据头部信息将收到的报文段交给正确的进程（Socket）。

> 如果某层的一个协议对应直接上层的多个协议/实体，则需要复用/解复用。

多路复用/解复用是依靠源和目的的IP地址、进程端口号来实现的。当发送端应用进程将消息交给传输层时，传输层会对消息进行封装，加上头部信息，其中就包括该进程和目的进程的端口号；当接收端网络层向传输层递交分组时，传输层提取出其中的源和目的IP地址、端口号以确定向哪个进程传递报文。

详细来说，UDP协议和TCP协议解复用时利用的信息是不同的。

UDP协议依据目的IP+目的端口号来标识Socket，源IP和源端口用做消息回送地址。如下图所示，主机P1和P2都向主机P3的6428端口发送数据，主机P3上端口号为6428的进程将接收消息，并利用返回地址分别向主机P1和P2发送反馈信息。

# UDP

UDP全名User Datagram Protocol。它基于网络层的IP协议，在其基础上只增加了一点点内容：

+ 复用/解复用；
+ 简单的端到端的错误校验；

可以说，UDP几乎将IP层服务暴露给了应用层。

UDP协议可能导致报文段的**丢失**、**乱序**。

![计算机科学/网络通信/assets/03. 计算机网络-传输层/c7d2ed746e3dca1e96e3bbfc092f0e38_MD5.png](/img/user/%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%A7%91%E5%AD%A6/%E7%BD%91%E7%BB%9C%E9%80%9A%E4%BF%A1/assets/03.%20%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%BD%91%E7%BB%9C-%E4%BC%A0%E8%BE%93%E5%B1%82/c7d2ed746e3dca1e96e3bbfc092f0e38_MD5.png)



## UDP校验和

目的：检查UDP段在传输过程中是否发生错误（如位翻转）。

校验算法：

+ 将段的内容看做一个个16比特的整数。
+ 计算所有整数的和，进位加在和的后面，将得到的值按位求反，得到校验和。
+ 发送方将校验和放入校验和字段。
+ 接收方按照同样流程计算校验和，将其和校验和字段的值进行对比，如果值不相等则检测出错误，如果值相等也可能存在错误。

从上面也能看出，校验算法存在检测能力限制。

![计算机科学/网络通信/assets/03. 计算机网络-传输层/ff43a8c2f2d64f0e5a3db42a99524689_MD5.png](/img/user/%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%A7%91%E5%AD%A6/%E7%BD%91%E7%BB%9C%E9%80%9A%E4%BF%A1/assets/03.%20%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%BD%91%E7%BB%9C-%E4%BC%A0%E8%BE%93%E5%B1%82/ff43a8c2f2d64f0e5a3db42a99524689_MD5.png)



## UDP的优点

+ 无需建立连接，延迟少（所以DNS使用的是UDP服务）；
+ 实现简单，无需维护连接状态；
+ 头部开销小；
+ 没有拥塞控制，应用层可以更好地掌控发送速率；



正因为这些优点，UDP常被用于流媒体应用，此外还被应用于DNS、SNMP。

尽管UDP本身不支持可靠性的保障，但是开发人员可以在应用层自己定义可靠性的保证机制，来使用UDP进行可靠数据传输。

## 处理位错误

假定信道只会发生位的翻转错误。首先需要检查是否出错，当出现错误时通知发送方重传。

+ 利用校验和检测位错误；
+ 接收方通过发送ACK/NAK给发送方；

这个过程中一共涉及到：校验机制、ACK机制、NAK机制和重传机制，基于这种方式的rdt协议称为**ARQ**协议。

![计算机科学/网络通信/assets/03. 计算机网络-传输层/d5c2bee1450f635721e527308ff00cb5_MD5.png](/img/user/%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%A7%91%E5%AD%A6/%E7%BD%91%E7%BB%9C%E9%80%9A%E4%BF%A1/assets/03.%20%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%BD%91%E7%BB%9C-%E4%BC%A0%E8%BE%93%E5%B1%82/d5c2bee1450f635721e527308ff00cb5_MD5.png)



## 处理ACK/NCK错误

ARQ协议存在一个缺陷：ACK/NAK消息传输可能会发生错误。解决的方法有：

+ 为ACK/NCK增加可以检错和纠错的校验和，实现较复杂。
+ 如果ACK/NAK坏掉，发送方认为是分组未正确被接收，并重传数据分组，但是需要解决**重复分组**的问题。

> **重复分组**是指接收方成功接收一个分组，但是发送方接收返回的ACK坏掉，于是发送方重传该分组，此时接收方无法判断该分组是重传的还是新的分组数据）

解决重复分组问题的方式是发送方为每个分组增加一个**序列号（只需要0和1两个序号就够了）**，接收方接收到序号重复的分组就丢弃。

这个过程中在原有基础上新增了**序列号机制**。因为发送方必须记住“当前”分组的序列号，所以导致了状态数量翻倍；而接收方则需要增加分组重复的判断。

## 无NAK消息协议

实际上，我们可以定义一个只使用ACK的消息协议，为了实现这样的目的，接收方需要通过ACK告知最后一个被正确接收的分组（即在ACK消息中显式地加入被确认分组的序列号）。

例如，发送方第一次发送序号为0的分组，并且接收的序号为0的ACK；然后发送方发送序号为1的分组，假设该分组发生错误，则接收方仍然返回序号为0的ACK，这样发送方就知道分组没有被正确收到，于是重传序号为1的分组。

![计算机科学/网络通信/assets/03. 计算机网络-传输层/3a7b2513cf3cfdbce9f82965895cbf01_MD5.png](/img/user/%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%A7%91%E5%AD%A6/%E7%BD%91%E7%BB%9C%E9%80%9A%E4%BF%A1/assets/03.%20%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%BD%91%E7%BB%9C-%E4%BC%A0%E8%BE%93%E5%B1%82/3a7b2513cf3cfdbce9f82965895cbf01_MD5.png)



## 处理错误+丢失

现在，我们将假设放宽，考虑可能发生错误，也可能发生丢失的信道。

在这样的条件下，“校验和+序列号+ACK+重传”已经不够用了，因为如果分组丢失，那么接收方就不会发送ACK消息，或者ACK半路丢失，发送方都会一直等待下去。

解决的方法也很简单，就是让发送方只等待一个合理的时间，超时还未收到ACK就重传。当然这种方法也存在不足：

+ 合理的等待时间难以确定。
+ 分组超时可能是因为信道延迟而不是丢失导致的，所以可能存在重传，但这还是在序列号机制的能力范围内，所以不是大问题。

这个过程中增加了**定时器机制**。

![计算机科学/网络通信/assets/03. 计算机网络-传输层/da1f9da7f02a5a96b5da63d11cfc5150_MD5.png](/img/user/%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%A7%91%E5%AD%A6/%E7%BD%91%E7%BB%9C%E9%80%9A%E4%BF%A1/assets/03.%20%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%BD%91%E7%BB%9C-%E4%BC%A0%E8%BE%93%E5%B1%82/da1f9da7f02a5a96b5da63d11cfc5150_MD5.png)



## 滑动窗口协议

定时器机制虽然有效解决了分组丢失的问题，但是它的性能很糟糕——发送方在发送一个分组之后必须等待接收端的响应。因此，改进协议的思想就是引入**流水线机制**，让发送方在等待响应的这段时间内可以继续发送新的分组。

![计算机科学/网络通信/assets/03. 计算机网络-传输层/1321099f1bd0d1dfb88f58544488f5a1_MD5.png](/img/user/%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%A7%91%E5%AD%A6/%E7%BD%91%E7%BB%9C%E9%80%9A%E4%BF%A1/assets/03.%20%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%BD%91%E7%BB%9C-%E4%BC%A0%E8%BE%93%E5%B1%82/1321099f1bd0d1dfb88f58544488f5a1_MD5.png)

流水线机制另一方面也要求收发双方必须作出以下牺牲：

+ 采用更大的序列号范围；
+ 发送方和接收方需要更大的存储空间以缓存分组；
+ 流水线也导致了分组发生乱序的问题；

流水线机制是通过**滑动窗口协议**来实现的，常见的分为GBN和SR协议两种（都能很好地应对乱序问题）。



### Go-Back-N

在GBN协议中，只有发送方需要维护窗口。窗口表示允许使用的序列号范围，假设窗口尺寸为N，则最多可以容纳N个等待确认的消息。如下图所示，随着协议的运行，窗口向右滑动，绿色部分表示已经确认的分组，黄色表示已经发送正等待确认的分组，蓝色部分表示剩余可容纳的分组空间。

![计算机科学/网络通信/assets/03. 计算机网络-传输层/fd6724a03fec04875b67551079678fb9_MD5.png](/img/user/%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%A7%91%E5%AD%A6/%E7%BD%91%E7%BB%9C%E9%80%9A%E4%BF%A1/assets/03.%20%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%BD%91%E7%BB%9C-%E4%BC%A0%E8%BE%93%E5%B1%82/fd6724a03fec04875b67551079678fb9_MD5.png)



GBN协议的最大特点是**累积确认机制**：

+ ACK(n)表示的是序列号n之前（包括n）的分组均已被正确接收。
+ 当发生超时事件时，发送方需要重传序列号大于等于n的所有分组。

如下图所示，窗口的滑动仅发生在每一次收到确认消息之时（变量`base`被改变），每次滑动之后，都会重置定时器。

![计算机科学/网络通信/assets/03. 计算机网络-传输层/5a2c9bb2bae85d66cdc87e3075ccfadb_MD5.png](/img/user/%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%A7%91%E5%AD%A6/%E7%BD%91%E7%BB%9C%E9%80%9A%E4%BF%A1/assets/03.%20%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%BD%91%E7%BB%9C-%E4%BC%A0%E8%BE%93%E5%B1%82/5a2c9bb2bae85d66cdc87e3075ccfadb_MD5.png)

GBN协议下，接收方的逻辑简单很多，因为不用缓存分组，只要维护一个`expectedseqnum`变量即可。例如接收方正在等待序列号为1的分组（`expectedseqnum=1`），当收到序列号为1的分组时，发送ACK(1)；接下来如果正在等待序号2，却收到了序列号为3的分组，说明发生了**乱序**，此时应该要发送ACK(1)。

### Selective Repeat

GBN协议最大的缺陷在于需要重传许多个分组，浪费了资源，这是累积确认机制导致的。SR协议则采用**单独确认机制**，即对每个分组进行单独确认，这样发送方就可以只重传那些没有得到确认的分组。但是单独确认的代价就是：

+ 接收方就需要设置**缓存机制**——缓存乱序到达的分组。
+ 要为每个分组单独设置定时器。

如下图所示，发送方的窗口和GBN协议中的一样，SR协议中接收方也需要一个滑动窗口，其中灰色和蓝色部分都表示正在等待接收的序列分组，紫色表示因为乱序而提前接收到的分组。每当窗口最左侧的分组接收到后，窗口便向右滑动，直至其最左侧是还未接收到的分组。

# TCP



## 特点

TCP协议具有以下特点：

+ 点对点：只能有一个发送方和一个接收方，不能一对多
+ 可靠的、按序的字节流
+ 支持流水线机制
+ 发送方和接收方都有设置缓存
+ 全双工
+ 面向连接：连接状态只在连接的两端中维护，沿途节点不维护状态
+ 拥塞控制、流量控制

## 可靠数据传输

### 概述

TCP在保证数据可靠性方面提供了以下机制：

+ 累积确认机制；
+ 流水线机制；
+ 重传机制：在超时、收到重复ACK时重传；
+ 单一定时器机制；
+ 流量控制机制；



### 超时时间估计

在TCP协议中，超时时间是根据实际测量的RTT动态自适应调整的。用`SampleRTT`表示测量从段发出去到收到ACK的时间，测量多个`SampleRTT`，其加权平均值用`EstimatedRTT`表示，其计算方式为：
$$
EstimatedRTT = (1-\alpha)*EstimatedRTT + \alpha*SampleRTT
$$
超时时间应该设置为`EstimatedRTT`再加上一个安全过渡区域，当`EstimatedRTT`变化较大时（方差较大），过渡区域应该越大。超时时间设置如下：
$$
DevRTT = (1-\beta)*DevRTT + \beta * |SampleRTT-EstimatedRTT|
$$

$$
TimeoutInterval = EstimatedRTT + 4*DevRTT
$$

### 快速重传机制

在TCP实现中，如果发生超时，超时时间间隔将重新设置为原来的两倍，导致丢失检查的滞后性较大。快速重传机制则是从另一个角度应对分组丢失，其思想是在流水线中，如果发送方发送的某个分组丢失，由于发送方还在不断发送新的分组，那么很可能会导致发送方短时间内接收到过个重复ACK，所以可以利用监测重复ACK的方法来进行猜测丢失并进行重传。

![计算机科学/网络通信/assets/03. 计算机网络-传输层/87a83488f2a2a6b31b4810871461575a_MD5.png](/img/user/%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%A7%91%E5%AD%A6/%E7%BD%91%E7%BB%9C%E9%80%9A%E4%BF%A1/assets/03.%20%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%BD%91%E7%BB%9C-%E4%BC%A0%E8%BE%93%E5%B1%82/87a83488f2a2a6b31b4810871461575a_MD5.png)

### 流量控制

接收方会为TCP连接分配Buffer，接收的段会存入Buffer中，传递给应用层的段则从Buffer中踢出，当发送方发送较快，应用层消耗较慢时容易导致Buffer溢出。因此TCP协议需要加入**流量控制机制**。流量控制本质上就是一个速度匹配机制。

TCP的流量控制就是接收方每次回应时通过段的头部字段`RcvWindow`告诉发送方自己的可用Buffer空间大小，接收方根据该大小调整自己的发送速率。

> 当RcvWindow=0时，发送方并不会停止发送，因为如果这样接收方即使之后有空余的Buffer空间，也没有机会将新的RcvWindow值告诉给发送方（接收方返回段不是主动的）。



### 连接管理



#### 三次握手

1. 客户端发送SYN段，段中标志位SYN置1，并携带客户机随机选择的一个初始序列号seq=J，SYN段不包含数据内容。
2. 服务器收到SYN段，回应SYNACK报文段，段中标志位SYN和ACK都置1，ack=J+1，随机产生序列号seq=K。同时，服务器为该连接分配资源（缓存）。
3. 客户端收到SYNACK后，回应ACK报文段，段中标志位ACK置1，ack=K+1。当服务器收到该ACK报文段时，连接便建立成功。

![计算机科学/网络通信/assets/03. 计算机网络-传输层/1335eaa7573b8b5886a9a8f7feed416e_MD5.png](/img/user/%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%A7%91%E5%AD%A6/%E7%BD%91%E7%BB%9C%E9%80%9A%E4%BF%A1/assets/03.%20%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%BD%91%E7%BB%9C-%E4%BC%A0%E8%BE%93%E5%B1%82/1335eaa7573b8b5886a9a8f7feed416e_MD5.png)

之所以采用三次握手，而不是二次握手是有原因的：

+ 在第二次握手时，服务器携带的序列号需要被客户机正确接收，因此客户端有必要回应通知服务器结果；
+ 假设当客户机发送了SYN段后，该段由于网络拥塞在某个节点长期滞留，然后客户端重传SYN段并最终和服务端建立了连接，在该连接关闭之后，最初的SYN段才到达，在二次握手机制下，服务器会认为这是新的一次连接请求，于是回应ACK，并一直等待客户机发送数据从而造成资源浪费。

此外，服务器在第二次握手期间就为连接分配了资源，当达到超时时间还未进行第三次握手，服务器就会释放资源。在这个过程中，存在安全隐患——攻击者可以利用上万台客户机同时向服务器发送TCP请求连接但是都不进行第三次握手，就会导致服务器资源的大量浪费（这是一种著名的网络攻击手段）。



#### 四次挥手

1. 客户端向服务器发送FIN段；
2. 服务器收到FIN段，回应ACK，并发送FIN段；
3. 客户端收到FIN，回复ACK，并进入固定时间的等待，如果再次收到FIN，则重新发送ACK；
4. 服务器收到ACK，服务器方的连接关闭；等到客户端等待时间过完，客户端方的连接也关闭；

## 拥塞控制

所谓拥塞，是指太多发送主机发送了太多数据或者发送速度太快以至于网络无法处理。

拥塞和流量控制有区别，流量控制是端和端的速度匹配，目的是不让接收方缓存溢出，而拥塞控制则是避免网络中的路由器或者链路过载。流量控制是点对点的通信量控制，而拥塞控制是全局的网络流量整体性的控制。

拥塞的主要成因是流量较大时，数据会在路由器中排队更严重时导致路由器缓存溢出，其表现为：

+ 分组丢失（路由器缓存溢出）
+ 分组延迟过大（在路由器缓存中排队）

拥塞造成的代价主要是延迟和资源浪费，一旦链路有拥塞，就会因为丢失或者定时超时使得重传现象增多；在多跳网络中，某个节点的拥塞导致的分组丢失，会使得用于该分组的所有上游节点的传输能力都被浪费掉。



### 控制方法

拥塞的控制方法可以分成两种：

+ 端到端的拥塞控制：端系统通过观察丢失和延时情况来判断网络的拥塞情况，网络层不需要提供显式的支持。
+ 网络辅助的拥塞控制：路由器向发送方显式地反馈网络拥塞信息，指示发送方采用何种速率，这需要网络层提供一定支持。

TCP采用的是端到端的拥塞控制方法。



### TCP拥塞控制算法

TCP拥塞控制的算法的核心就是通过拥塞窗口来限制发送速率，拥塞窗口的大小根据网络拥塞情况动态调整（这和流量控制比较相似）。发送方感知网络拥塞的主要是监听两个事件：3个重复ACK、超时，这两个事件对应的处理方式不同，因为超时说明网络拥塞要比3个重复ACK更严重一些。

在窗口调整策略上，有两种策略：加性增-乘性减、慢启动。

+ 加性增-乘性减：每成功收到一个非重复ACK，拥塞窗口增加一个MSS；监测到拥塞事件时，将拥塞窗口大小减半。
+ 慢启动：拥塞窗口初始大小等于一个MSS，之后每成功收到一个非重复ACK，窗口大小翻倍；

TCP拥塞控制算法结合了这两种策略，其过程如下：

+ 连接建立时，拥塞窗口大小等于1MSS；

+ 当拥塞窗口尺寸小于阈值T时，发送方进入**慢启动阶段**，窗口大小指数增长（翻倍）；
+ 当拥塞窗口尺寸大于阈值T时，发送方进入**拥塞避免阶段**，窗口大小线性增长；
+ 当发生**3次重复ACK事件**时，阈值T设置为此时窗口大小的一半，然后窗口大小减半；
+ 当发生**超时事件**时，阈值T设置为此时窗口大小的一半，然后窗口大小设置为1MSS；

# 音视频为什么用UDP

+ 低延迟优先于可靠性；
+ 丢包可以容忍（人眼人耳有容错）；
+ 没有拥塞控制，应用层可以更好地掌控发送速率；
+ UDP的头部开销更小，对于高频率、小包传输的音视频数据整体传输效率更高；
+ UDP 支持广播和组播：在在线直播课堂或大型会议中，如果使用 TCP，服务器需要给 1000 个用户建立 1000 个连接并重复发送 1000 次数据。而 UDP 可以通过组播技术，一次发送让多个用户接收，节省带宽；
+ 虽然实时音视频用了 UDP，但并不代表它就真的在“裸奔”传输原始数据，在应用层实现一定程度可控的可靠性；（I帧重传、前向冗余数据纠错、自适应码率）
