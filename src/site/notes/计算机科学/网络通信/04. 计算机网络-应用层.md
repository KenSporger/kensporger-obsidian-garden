# 主要功能

应用层直接为应用进程提供常见的网络应用服务，例如Web服务、Email服务等等。



# 网络应用的结构

## 客户/服务器结构（C/S）

![C/S结构](https://s2.loli.net/2022/04/22/E3Nx2HjqGFoUQLa.png)

服务器特点：

+ 7*24小时提供服务；
+ 提供永久性访问自身的地址/域名；
+ 利用大量服务器主机实现高并发；



客户机特点：

+ 使用服务器提供的服务；
+ **间歇性**接入网络；
+ 可能使用**动态IP**地址；
+ **不会与其他客户机直接通信**；



典型应用：Web、数据库MySQL。



## 点对点结构（P2P）

+ 主机都是**平等**的；
+ 任意端系统/节点之间可以**直接通信**；
+ 节点间**间歇性**连入网络；
+ 节点可能使用**动态IP**地址；

典型应用：迅雷。



## 混合结构

兼具C/S和P2P的优点。

典型应用：Napster。

+ 文件传输使用P2P结构；
+ 文件的搜索采用C/S结构；

![Napster采用的混合结构](https://s2.loli.net/2022/04/22/LesZahYCpGr6kgw.png)





## 应用层协议

应用层协议分为公开协议和私有协议。

+ 公开协议标准由RFC组织定义，可以在RFC组织官网找到相关协议的文档。该类协议有HTTP、SMTP等等。

+ 私有协议是出于商业竞争而保密的协议，例如多数P2P文件共享应用。

协议的内容一般包括：

+ 消息的类型：如HTTP协议规定了两种类型，即请求消息和响应消息。
+ 消息的语法格式：比如消息中有哪些字段，每个字段如何描述等。
+ 字段的语义：字段中信息的含义。
+ 规则：进程何时发送和响应消息、进程如何发送和响应消息等。



## 网络应用的服务需求

+ **可靠性**：某些应用容许一定的数据丢失，例如网络电话；有些应用则要求100%可靠的数据传输，例如文件传输。
+ **时延**：有些应用只有在低时延的条件下才有效，例如网络电话。
+ **带宽**：有些应用只有在高带宽（速率）的条件下才有效，例如网络视频；有些应用则能够适应任何带宽，如email。

网络层的协议是依赖于传输层协议的，传输层提供了两种等级的传输服务：TCP和UDP。

Web应用采用HTTP协议进行数据传输。

## HTTP协议特点

+ HTTP是超文本传输协议。
+ 采用C/S架构，下图中的Apache是最常见的Web服务器端软件。

![HTTP协议的C/S模型](https://s2.loli.net/2022/04/22/4rVBlqiCtskPYHy.png)

+ 使用TCP传输服务。

+ **无状态协议**：服务器不维护有关客户机关于过去所发请求的信息。之所以采用无状态的协议是因为：
  + 维护状态需要额外的开销；
  + 如果客户机或服务器失效，就会产生状态的不一致，解决不一致问题的代价较高。

+ HTTP连接有两种类型：非持久连接（HTTP1.0默认采用的方式）和**持久连接**（HTTP1.1默认采用的方式）。
  + 非持久连接：每个TCP连接最多允许传输一个对象；例如在浏览器中输入`www.abc.com/122/home.index`
    + 步骤1：HTTP客户端向地址为`www.abc.com`的服务器上的HTTP服务器进程发起TCP连接请求。
    + 步骤2：HTTP服务器在端口80等待TCP连接请求，接受连接并通知客户端。
    + 步骤3：HTTP客户端将HTTP请求通过TCP连接的套接字发出，其中包含请求对象的地址`122/home.index`。
    + 步骤4：HTTP服务器接收到请求消息，产生包含所需要对象的响应消息，并通过套接字发送给客户端。
    + 步骤5：HTTP服务器关闭TCP连接。
    + 步骤6：HTTP客户端接收到响应消息，解析HTML文件，显示HTML文件，发现有10个指向jpg对象的超链接。
    + 为每个jpg图片重复步骤1-6。
  + 持久连接：非持久性连接存在的问题是存在很多不必要的TCP连接过程，给客户端和服务器带来了负担。因此持久性连接在连接建立后，服务器会保持TCP连接直到所有对象传输完毕。持久连接又可以细分为两类：
    + 无流水的持久性连接：客户端只有在收到前一个请求的响应后才发送新的请求；
    + 带流水机制的持久性连接：客户端只要遇到一个引用对象就尽快地发出请求；

## HTTP版本演变



### HTTP1.0到HTTP1.1

HTTP1.0采用的是**短连接**方式，一次连接只发送一次请求，这样就存在过多的连接延迟。HTTP1.1采用了**长连接**的方案，并引入**流水线**机制，一次连接中可以请求多次，并且下一次请求不必等待上一次请求被响应时才发送，这样减少了整体的响应时间。但是，由于服务器在一次连接中总是按请求到来的顺序响应，如果第一次请求处理得比较慢，则会阻塞之后的请求，所以HTTP1.1引入了著名的**队头阻塞**问题。



### HTTP2

HTTP2相对于HTTP1.1做出了一下改进：

+ **头部压缩**：通常来说，前后多个HTTP请求的头部字段有些是一样的，所以可以避免对相同头部字段的重复发送，从而减少头部长度。其实现方法是在客户端和服务端同时维护一张头部字段缓存表，每个字段对应一个唯一索引，当客户端发送重复头部字段时，发现缓存表中已经有这个字段，就会替以索引号进行发送。
+ **二进制格式**：HTTP1.1的报文格式是纯文本形式的，而HTTP2则全面采用了二进制格式。
+ **多路复用**：类似于SPDY协议，允许多个并发 HTTP 请求共用一个 TCP会话。
+ **服务器推送**：HTTP1.1是请求-应答的拉取模式，服务器只能被动响应；在HTTP2中，服务器在一些情况下可以进行主动推送。
+ **强制SSL传输**。





## Cookie/Session技术

HTTP协议是无状态的，但是很多Web应用如网上购物，需要掌握客户端的历史状态。所以服务器为了记录用户信息，在用户第一次连接时会为该用户创建一个**Session**，Session保存在服务端，可能是内存中、数据库或者文件中。为了辨别每个用户，服务器还会为每个用户分配一个SessionID，这个id就唯一标识了该客户，可以用来查找对应的Session数据。SessionID是通过**Cookie技术**存储在客户端的。

Cookie技术是网站为了辨别用户身份、进行Session跟踪而**存储在用户本地**的经过加密的数据。

![Cookie的原理](https://s2.loli.net/2022/04/22/Swx75a4yg8NERYL.png)

如上图所示，用户第一次访问amazon服务器时，服务器会分配一个ID给客户端，同时将ID和客户端信息保存到数据库中，并在响应消息中告诉客户端它的Cookie ID，客户端接收到响应后，将网站和对应ID保存到Cookie File中。当客户端第二次访问服务器时，服务器就会查询到有关该客户的历史信息并返回。

Cookie技术也存在弊端，主要是隐私问题。



## 缓存/代理服务器技术

![缓存/代理服务器](https://s2.loli.net/2022/04/23/kYuSIT5zPcOtipX.png)

**Web缓存/代理技术指的是在不访问目的服务器的前提下满足客户端的HTTP请求**。该技术的主要作用是缩短客户请求的响应时间，减少机构/组织的流量。

Web缓存需要考虑的问题是代理服务器上的资源是否是最新的，为此代理服务器有必要使用条件性GET方法，即在请求消息中声明所持有对象的版本日期。如果版本是最新的，则目标服务器返回给缓存服务器304状态码，并且响应消息不包含对象；反之服务器返回缓存服务器最新版本的对象。

![条件性GET](https://s2.loli.net/2022/04/23/REYG4L5JCsVWvpF.png)



# Email应用

![Email应用](https://s2.loli.net/2022/04/22/aYcCUM8WKbJmFrQ.png)

Email应用的组件包括：客户端（发送邮件）、服务器（接收邮件）和SMTP协议。其中Email服务器是应用的核心，例如163、qq邮箱服务器等。普通的用户需要向邮箱服务器申请一个账号，邮箱服务器存储用户收到的邮件以及等待发送的邮件。采用邮箱服务器的一个好处就是24小时在线，即使接收方用户不在线，也可以发送邮件。



## SMTP协议

+ SMTP只用于客户端向服务器上传邮件，不支持客户端访问服务器上的邮件。

+ 使用TCP进行可靠传输。

+ 端口号是25。

+ 传输过程：握手、消息传输、关闭。

+ 采用命令-响应模式（HTTP是请求-响应模式）。

  SMTP常用的命令有：HELO、MAIL FROM、RCPT TO、DATA、QUIT。

+ Email消息只能包含7位ASCII码。

+ 使用持久性连接。



交互示例（使用telnet）：

1. 使用telnet连接smtp服务器；
2. 发送一个HELO指令；
3. 验证用户；
4. 使用MAIL FROM命令准备发送邮件;
5. 使用RCPT命令指定对方邮箱地址；
6. 使用DATA命令开始输入内容；
7. 输入邮件内容；
8. 输入邮件内容结束标志（.）;
9. 退出SMTP服务器；

# DNS应用

DNS解决的是主机/路由器的识别问题。服务器有唯一的IP地址，但是这个IP难以记忆，因此就引入了域名，关键的问题在于如何将域名解析为IP地址。

由于全世界存在几十亿台主机，要保证解析的实时性，其解决方案是非常复杂的。

DNS提供的服务主要有：

+ 域名解析为IP地址；
+ 主机别名；
+ 邮件服务器别名；
+ 负载均衡：一个域名轮流映射到一组IP地址中的一个，从而实现流量的均衡；

# P2P应用

目前为止所讲的Web、Email、DNS都是CS架构，P2P则是点对点结构。P2P相比于CS架构的应用来说，优势在于能够实现高效的文件分发。



## BitTorrent协议

![BitTorrent文件分发](https://s2.loli.net/2022/04/22/Xj7QKLO1RN5Cvnw.png)

在BitTorrent协议网络中，文件被划分为256KB的一个个chunk。用户节点可以向tracker注册以加入Torrent并获得节点清单，并根据清单和其他节点连接。

一开始用户节点没有chunk，但随着下载会逐渐累积。节点下载的同时，该用户有义务向其他节点上传。一旦节点获得完整文件，它可能（自私地）离开或（无私地）留下。



chunk的交换过程如下：

+ 获取chunk
  + 任意时刻，不同节点持有文件的不同chunk集合；
  + 节点A定期查询每个邻居所持有的chunk列表；
  + 节点A按照稀缺优先原则（持有某个chunk的节点数最少）向一些节点发送请求，获取缺失的chunk；
+ 发送chunk
  + 节点A同时向4个其他节点发送chunk，这四个节点是：正在向其发送的节点或者速率最快的4个节点。
  + 每30秒随机选择一个其他节点。

总之，BT的交换潜则就是：节点上传速率越高，就能更快地下载资源。



## 索引技术

P2P应用中经常需要搜索信息，所以需要一个高效的索引体系。



### 集中式索引

节点加入时，将其信息通知给服务器，节点要查询资源时也是向服务器进行请求，服务器返回资源的持有者列表。

集中式索引存在单点失效问题（服务器崩掉）、性能瓶颈。



### 洪泛式查询

是完全分布式的，某个时刻有着TCP连接的节点组成一个图，可以运用图搜索的方法逐层访问各个节点，从而获取到全网的资源信息。洪泛式查询的问题是网路的负担较大。

![洪泛式查询](https://s2.loli.net/2022/04/23/IZ4bs8pejPn7VDw.png)



### 层次式覆盖网络

是介于集中式和完全分布式之间的方法。网络中存在普通节点和超级节点。

# 进程通信

网络应用的通信本质上是进程间通信。

进程间网络通信是通过套接字socket来实现的。socket是操作系统提供的一种抽象（API），进程通过套接字来使用下层的网络协议栈。

![网络进程通信](https://s2.loli.net/2022/04/23/eCdZJQhO37qciWG.png)

不同主机上的进程间通信，为了能够寻址进程，每个进程就必须拥有标识符（IP+端口号）。

+ IP地址用于寻址不同主机；
+ 端口号用于定位主机上的进程；

## 网络编程接口API

应用层的两个程序进程进行网络通信，遵循应用层的协议，但不是直接通讯的，而是要经过底下的几层。应用层调用传输层服务的接口称为**网络编程接口API**，它是一个系统调用接口（传输层属于操作系统控制的部分，应用进程调用API，把控制权交给操作系统，由操作系统执行相应操作，并返回结果给应用层）。

现有的典型的网络编程接口有：基于UNIX的套接字（Socket）、基于Windows的套接字接口WINSOCK、为UNIX系统V定义的接口TLI。

这里主要介绍的是WINSOCK。



## Socket抽象

套接字是面向TCP/IP协议栈的接口，适用于客户/服务器通信。

由于客户和服务器都能创建套接字，每个进程还可以创建多个套接字，因此需要标识出套接字：

+ 对外：IP地址+端口号；
+ 对内：套接字描述符；

每个进程都拥有一个套接字描述符表，每当该进程创建一个套接字时，操作系统分配一个空间存放Socket数据结构，并返回给进程一个**套接字描述符**。套接字描述符表中每一项记录都指向一个Socket数据结构。

![套接字描述符](https://s2.loli.net/2022/04/22/XWJFYo4n63kNmOh.png)

Socket的端点地址变量结构。

```c
struct sockaddr_in
{
  	u_char sin_len;				// 地址长度
    u_char sin_family;			// 地址族（TCP/IP为AF_INET）
    u_short sin_port; 			// 端口号
    struct in_addr sin_addr;	// IP地址
    char sin_zero[8];			// 保留
};
```



## API函数

### WSAStartup

使用Socket的应用程序必须首先调用该函数来进行初始化。

```cpp
// wVersionRequested:指明程序要使用的WinSocket版本
// IpWSAData:实际使用的版本
// 返回：初始化是否成功
int WSAStartup(WORD wVersionRequested, LPWSADATA IpWSAData);
```



### WSACleanup

应用程序完成对Socket的使用之后，最后要调用该函数释放资源。



### socket

创建套接字。

```cpp
// protofamily:协议族，例如protofamily=PF_INET表示TCP/IP族
// type：套接字类型
// proto：协议号
// 返回：套接字描述符
sd = socket(protofamily, type, proto);
```

TCP/IP协议族下套接字类型包括：

+ SOCK_STREAM：采用TCP协议；
+ SOCK_DGRAM：采用UDP协议；
+ SOCK_RAW：直接面向网络层协议；



### CloseSocket

关闭一个描述符为sd的套接字，如果多个进程共享一个套接字，调用该函数使得引用计数减1，减至0时释放数据结构；但是一个进程中的多个线程对一个套接字的共享不采用引用计数方法，只要有一个线程关闭了套接字，其他线程就不能再访问该套接字。

```cpp
int closesocket(SOCKET sd);
```





### bind

绑定套接字的本地端点地址（IP+端口号）。客户端程序一般不必调用bind函数，操作系统会自动设置；服务器端必须调用，当有多个网卡时，还可以传入地址通配符INADDR_ANY（端口号固定，IP任意）。

```cpp
//localaddr：端点地址，即上文中的sockaddr_in数据结构
int bind(sd, localaddr, addrlen);
```



### listen

服务器端设置套接字处于监听状态。

```cpp
int listen(sd, queuesize);
```



### connect

TCP协议下，客户端调用该函数发起对服务端Socket的连接请求。

UDP协议下，客户端调用该函数指定服务器端点地址。

```
connect(sd, saddr, saddrlen);
```





### accept

仅用于TCP套接字，服务器端调用该函数从客户连接请求队列中取出一个连接请求，并且创建一个新的套接字来与客户套接字创建连接通道，之后服务器使用新的套接字和客户通信（这样的机制可以实现服务器并发）。

```
newsock = accept(sd, caddr, caddrlen);
```



### send/sendto

send函数用于TCP套接字（客户或服务器端）或调用了connect函数的UDP客户端套接字。

sendto函数用于UDP服务器端套接字和未调用connect函数的UDP客户端套接字。

```cpp
send(sd, *buf, len, flags);
sendto(sd, *buf, len, flags, destaddr, addrlen);
```



### recv/recvfrom

recv函数用于TCP套接字（客户或服务器端）或调用了connect函数的UDP客户端套接字从服务端接收信息。

recvfrom函数用于UDP服务器端套接字和未调用connect函数的UDP客户端套接字接收对端数据。

## 解析函数

### 解析服务器IP地址

客户端可以使用域名或IP地址标识服务器，而IP协议需要使用32位二进制IP地址，所以需要将域名或点分十进制IP地址转换为32位IP地址。

+ `inet_addr()`：实现点分十进制IP到32位IP地址的转换；
+ `gethostbyname()`：实现域名到32位IP地址转换；

这两个函数的返回都是一个指向结构`hostent`的指针。

```c++
struct hostent{
    char FAR*		h_name;
    char FAR* FAR*	h_aliases;
	short 		    h_addrtype;
    short 			h_lengty;
    char FAR* FAR* 	h_addr_list;
};
```



### 解析服务器端口号

客户端可能使用的并不是具体的端口号，而是服务名（如HTTP）来标识服务器端口。此时就需要用函数`getservbyname()`将服务名转换为熟知的端口号，该函数返回一个指向结构`servent`的指针。

```c++
struct servent{
	char FAR*		s_name;
	char FAR* FAR*	s_aliases;
	short 			s_port;
	char FAR*		s_proto;
};
```



### 解析协议号

客户端可能使用协议名（如TCP）指定协议，此时需要通过函数`getprotobyname()`将协议名转换为协议号（如6）。类似的，该函数返回一个指向结构`protoent`的指针。

```c++
struct{
	char FAR*		p_name;
	char FAR* FAR*	p_aliases;
	short 			p_proto;
};
```





## 客户端设计

（可以通过多态的方式设计一个TCP/UDP双协议客户端软件）

### TCP客户端

1. 确定服务器IP地址和端口号；
2. 创建套接字；
3. 分配本地端点地址（IP地址+端口号）；
4. 连接服务器；
5. 遵循应用层协议（例如推协议和拉协议）进行通信；
6. 关闭连接；



### UDP客户端

1. 确定服务器IP地址和端口号；
2. 创建套接字；
3. 分配本地端点地址（IP地址+端口号）；
4. 指定服务器端点地址，构造UDP数据报；
5. 遵循应用层协议进行通信（一定是UDP客户端先发信息）；
6. 关闭套接字；



## 服务器设计

4种基本服务器：循环无连接服务器、循环面向连接的服务器、并发无连接服务器、并发面向连接的服务器。



### 循环无连接

1. 创建套接字；
2. 绑定端点地址（INADDR_ANY+端口号）；
3. 反复接收来自客户端的请求；
4. 遵循应用层协议，构造响应报文，发送给客户；



### 循环面向连接



1. 创建主套接字，绑定端点地址；
2. 设置主套接字为被动监听模式；
3. 调用`accept`函数接收下一个连接请求，创建新套接字用于和该客户建立连接；
4. 遵循应用层协议，反复接收客户请求，构造并发送响应；
5. 完成为特定客户的服务后，关闭和该客户之间的连接，然后返回步骤3；



### 并发无连接



1. 主线程创建套接字，绑定端点地址；
2. 主线程反复调用`recvfrom`函数接收下一个客户请求，并创建新线程处理该客户响应；
3. 子线程依据应用层协议构造响应报文，并调用`sendto`发送，主线程循环第2步；
4. 子线程退出，主线程循环第2步；



### 并发面向连接

1. 主线程创建主套接字，绑定端点地址；
2. 主线程设置主套接字为被动监听模式；
3. 主线程反复调用`accept`函数接收下一个连接请求，并创建新套接字和新线程处理该客户响应；
4. 子线程用新套接字依据应用层协议和客户端交互，主线程循环第2步；
5. 子线程释放套接字并退出，主线程循环第2步；
