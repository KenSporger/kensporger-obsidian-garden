# 问题描述

dji-baselib库的 `json_dto.hpp`中定义`from_json`实现如下：

```cpp
//! Helper function to read DTO from json-string.
template< typename Type, unsigned Rapidjson_Parseflags = rapidjson::kParseDefaultFlags >
Type
from_json( const std::string & json )
{
	rapidjson::Document document;
	json_input_t jin{ document };

	document.Parse< Rapidjson_Parseflags >( json.c_str() );

	check_document_parse_status( document );
    std::cout << "check_document_parse_status ok" << std::endl;
	Type result;
    
	jin >> result;

	return result;
}
inline void
check_document_parse_status(
	const rapidjson::Document & document )
{
	if( document.HasParseError() )
	{
		throw ex_t{
			std::string{ "JSON parse error: '" } +
			rapidjson::GetParseError_En( document.GetParseError() ) +
			"' (offset: " + std::to_string( document.GetErrorOffset() ) + ")" };
	}
}
```

dji-baselib库中的`djivalue.cpp`中定义`MeidaFileConfig`的`FromJson`：
 
```cpp
bool MeidaFileConfig::FromJson(const std::string &json) {
    try {
        *this = json_dto::from_json<MeidaFileConfig>( json );
    }
    catch(...)
    {
        LOGW<<"[DJIValue] MeidaFileConfig FromJson error,str = " << json;
        return false;
    }
    return true;
}
```

在CSDK中，使用了rapidjson做json解析，rapidjson在处理非法字符串的时候会段错误，CSDK对此做了异常捕获。但有一天发现，当MeidaFileConfig::FromJson传入非法json字符串时，try_catch未成功捕捉到json_dto::from_json中抛出的异常导致程序crash。


# 排查过程

## 定位具体的位置

```cpp
template< typename Type, unsigned Rapidjson_Parseflags = rapidjson::kParseDefaultFlags >
Type
from_json( const std::string & json )
{
	rapidjson::Document document;
	json_input_t jin{ document };
	Type result;
	std::cout << "1" << std::endl;
	try {
		document.Parse< Rapidjson_Parseflags >( json.c_str() );
		check_document_parse_status( document );
		jin >> result;
	} catch(...) {
		std::cout << "2" << std::endl;
	}
	return result;
}
```

document.Parse< Rapidjson_Parseflags >( json.c_str() ); 发生了段错误（也可能是`jin >> result`），但是没有被catch住（只打印了1，没有2）。

## 了解C++异常无法捕获的情况

除了未捕获、捕获类型与抛出类型不匹配这些情况外，还有几种比较容易忽视的情况。

### 编译禁止异常

可以通过下面代码来禁止异常，禁止后如果代码中有try…catch、throw将会导致编译错误

```C++
set(CMAKE_CXX_FLAGS "${CMAKE_CXX_FLAGS} -Werror=return-type -fno-exceptions")
```

### **noexcept函数中抛出异常**

申明throw_runtime_local_from_libxtts为noexcept，但是仍抛出异常：

```C++
void throw_runtime_local_from_libxtts() noexcept {
    throw std::runtime_error("throw_runtime_local_from_libxtts");
}
```

编译运行会崩溃。

```C++
root@v1_ea230_dock:/ # /system/bin/tts_test                                                                                                                             
terminating with uncaught exception of type std::runtime_error: throw_runtime_local_from_libxtts
Aborted (core dumped) 
```

### 析构函数中抛出异常

在栈展开的过程中，退出某个块后，块内的局部对象将执行析构函数。因为这些析构函数是自动执行的，所以他们不应该抛出异常。一旦在栈展开的过程中析构函数抛出异常，并且析构函数没有捕获到该异常，则程序将终止。

```C++
class A {
public:
    ~A() {
        try {
            throw "throw 1";
        } catch (...) {
            cout << "catch 1" << endl;
        }
        throw "throw 2";
    }
};

int main(int argc, char* argv[]) {
    try {
        A a;
        throw "throw 3";
    } catch (...) {
        cout << "catch 3" << endl;
    }
	return 0;
}
```

运行结果如下：

```C++
linker.lu@linkerludeMacBook-Pro csdk_learning % ./demo 
catch 1
libc++abi: terminating due to uncaught exception of type char const*
zsh: abort      ./demo
```

### 动态链接库或线程边界异常

- **跨模块/线程异常**：如果异常在动态库中抛出，但在主程序中捕获（或反之），且编译选项（如异常模型）不一致，可能导致未定义行为。
	- 检查是否所有模块使用相同的编译器、C++标准库版本（如 libstdc++ 和 libc++ 混用会导致问题）。
	- 确保所有模块编译时启用了异常支持（如 GCC 的 `-fexceptions`）。
    
- **线程间异常**：C++11 后，跨线程的异常需要通过 `std::future` 等机制传递，直接抛出会导致异常丢失。

### 异常钩子

大型工程中可能存在全局异常处理钩子（如信号处理、SEH、第三方库的异常拦截），导致异常未到达 `catch(...)`。检查工程中是否有 `std::set_terminate` 或信号处理函数覆盖了默认行为。

## 原因假设

根据上面这么多原因，将排查范围缩小到异常钩子、以及跨模块的c++标准版本、异常禁止编译选项上。检查了CSDK代码里没有异常钩子，那最大可能跟跨模块、库有关。

为了排查问题所在的依赖库以及模块干扰，隔离测试环境——在大型工程中创建一个与最小测试程序完全相同的调用路径，只包含了核心的两个仓库，编写了一个CMakeLists.txt，是可以catch住异常的。
推断是由于 **异常处理机制在不同编译/链接环境下的差异** 导致的。
+ **不同的优化选项**（如 `-O2` vs `-O0`），`-fexceptions`、`-fno-exceptions`
+ 如果 `json_dto::from_json` 抛出的异常类型在大型工程中被 **重新定义**（如不同的 `ex_t` 类），可能导致 `catch(...)` 无法捕获。
+ 

进一步排查：
+ 逐步添加依赖库，直到异常捕获失败，定位冲突点。
+ 检查动态库的符号可见性：`ex_t`、`cxa_throw`等。

在链接了科大讯飞libxtts库后，反编译发现throw_ext_from_libxtts被优化掉了——没有`__cxa_throw`

## 根因

1. **根本原因：C++运行时库冲突**
    - [libxtts.so](https://libxtts.so/)内部静态链接了C++标准库（c++\_static），导致其异常处理函数（如__cxa_throw）独立于可执行文件。
    - 可执行文件默认使用c++\_static时，两个模块拥有不同的运行时实例，异常类型信息(RTTI)和异常处理函数地址不匹配，导致catch块无法识别抛出的dji_ex_t异常。
2. **添加c++\_shared生效的原因**
    - 强制可执行文件动态链接c++\_shared库，[libxtts.so](https://libxtts.so/)内部未完全静态链接运行时（或符号被覆盖），两者共享同一套异常处理机制。
    - 动态库的__cxa_throw被统一使用，确保异常抛出和捕获的运行时环境一致，RTTI匹配成功。

# 修复方式

## 懒加载

在编译阶段不链接tts库，在运行时加载。

```C++
// catch_test.cpp
\#include <iostream>
\#include "throw_test.hpp"
\#include <dlfcn.h>

void* handle_ = nullptr;

bool LoadLibtts() {
    // 加载共享库
    handle_ = dlopen("libtts.so", RTLD_LAZY);
    if (!handle_) {
        std::cerr << "LoadLibtts failed: " << dlerror() << std::endl;
        return false;
    }
    return true;
}

int main() {
    LoadLibtts();
    /*
    ....
    */
    return 0;
}
```
