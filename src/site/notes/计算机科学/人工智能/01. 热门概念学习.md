# MCP

模型上下文协议（Model Context Protocol），由Claud母公司Anthropic于2024年提出的协议，用于规范各种工具、资源接入LLM的接口格式。

## 架构

![01. 热门概念学习-1772947265840.png](/img/user/%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%A7%91%E5%AD%A6/%E4%BA%BA%E5%B7%A5%E6%99%BA%E8%83%BD/assets/01.%20%E7%83%AD%E9%97%A8%E6%A6%82%E5%BF%B5%E5%AD%A6%E4%B9%A0/01.%20%E7%83%AD%E9%97%A8%E6%A6%82%E5%BF%B5%E5%AD%A6%E4%B9%A0-1772947265840.png)

MCP包括以下组件：
+ MCP Host（主机）：即上图中的AI applications，LLM包含在主机中，例如由 AI 赋能的 IDE 或对话式 AI。
+ MCP 客户端/服务器：负责LLM格式与MCP格式的之间的转换；对于服务器而言，还提供工具、服务（上图中的右侧）。
+ 传输层：客户端与服务端之间的通信协议，本地调用使用stdio方式，远程调用通过Streamable HTTP协议完成。

## 工作原理

MCP的工作流程：工具发现→调用→外部操作→结果返回→最终响应，举例如下：

1. 用户向AI询问“明天的天气怎么样”；
2. LLM 首先分析自身能力边界，没有实时天气数据能力，于是调用 MCP 客户端，扫描已配置的 MCP 服务器列表，检索可用工具server-weather，这个配置是用户填入的，可能如下：
```json
{
  "mcpServers": {
    "weather": {
      "command": "npx",
      "args": ["@modelcontextprotocol/server-weather"],
      "env": {
        "WEATHER_API_KEY": "your_openweather_api_key_123456", // 天气 API 密钥
        "DEFAULT_LOCATION": "Beijing" // 默认城市（可选）
      }
    }
  }
}
```
3. LLM 生成符合 MCP 协议规范的结构化请求，核心参数包括：工具名称（weather_query）、查询参数（时间、地点等）、请求格式（ JSON/RPC 规范）等；
4. MCP 客户端将该结构化请求加密、标准化后，发送到对应的「天气查询 MCP 服务器」；
5. 天气查询 MCP 服务器接收请求后，进行参数校验和标准化；
6. 服务器使用用户预配置的天气 API 密钥调用第三方天气 API（如墨迹天气）；
7. 第三方天气 API 返回结构化数据，MCP 服务器将返回数据格式化，并通过 MCP 协议回传给 LLM；
8. LLM 接收天气数据后，将其转化为自然语言回答；

# RAG

![01. 热门概念学习-1772956274925.png](/img/user/%E8%AE%A1%E7%AE%97%E6%9C%BA%E7%A7%91%E5%AD%A6/%E4%BA%BA%E5%B7%A5%E6%99%BA%E8%83%BD/assets/01.%20%E7%83%AD%E9%97%A8%E6%A6%82%E5%BF%B5%E5%AD%A6%E4%B9%A0/01.%20%E7%83%AD%E9%97%A8%E6%A6%82%E5%BF%B5%E5%AD%A6%E4%B9%A0-1772956274925.png)

RAG 是一种增强Prompt的技术。首先通过LLM embeding的技术将用户自己定义的数据向量化，当用户发起查询时候，再通过LLM embeding去从向量库中找到有关上下文知识添加到Prompt中，大模型根据提供的Prompt结合自己本身的训练进行推理。所以LLM本身是一个“CPU”，而RAG像是一个“存储器”，不同LLM的差异体现在对不同Prompt的推理能力上。


# Agentic Search
{ #15d420}


Anthropic推出的Claude Code AI助手没有采用传统的RAG技术，而是使用了代理式搜索：调用工具（ls/glob/grep）来定位文件，read读取文件作为模型的输入，就像一个程序员一样一步步自己去翻代码。

一个例子如下：
1. 用户提问：帮我看一下项目里的登录逻辑，有没有安全问题？
2. 通过`list_dir`（MCP技术调用VsCode工具）获取项目结构，找到登录相关文件`login.js`；
3. 读取`login.js`，模型判断还需要看接口，通过`search_files("login", "api/")`，找到：`src/api/auth.js`，再读取`auth.js`文件；
4. 模型现在拥有login页面源码、登陆接口、可能的权限、加密、token逻辑。

| 对比项        | Agentic Search                 | RAG                    |
| :--------- | :----------------------------- | :--------------------- |
| 核心实现逻辑     | AI 自主调用 grep/glob 等终端工具，实时探索检索 | 预向量化建库，查询时通过语义匹配召回内容   |
| 初始化 & 维护成本 | 零成本，即开即用，无额外基础设施依赖             | 高成本，需持续维护索引、向量库与嵌入服务   |
| 数据新鲜度      | 实时，直接读取当前最新的原始文件               | 有延迟，增量内容需重新索引才能被召回     |
| 代码场景检索精度   | 大幅领先，完美适配代码结构与关键词匹配            | 较弱，分片易破坏代码结构，语义匹配易失真   |
| Token 开销   | 偏高，多轮迭代探索会增加上下文 Token 消耗       | 低，单次检索，Token 开销稳定可控    |
| 可解释性       | 高，每一步工具调用全透明、可追溯               | 低，向量相似度匹配为黑盒，召回逻辑不可控   |
| 安全隐私性      | 优秀，按需读取文件，代码主体全程留在本地           | 中等，需全量内容向量化存储，存在数据外流风险 |
| 最优适配场景     | 代码开发、高频更新的结构化文件管理              | 静态文档、知识库、非结构化长文本问答     |
